# Task 3. Проблемы и риски текущей архитектуры InsureTech

## Контекст
Сервисы `core-app` и `ins-comp-settlement` получают данные о продуктах и тарифах через REST-интеграцию с `ins-product-aggregator`, который синхронно опрашивает 5 страховых компаний. Параллельно `ins-comp-settlement` ежесуточно по REST вытягивает из `core-app` список оформленных страховок. InsureTech планирует подключить ещё 5 страховых компаний.

## Проблемы

### 1. Каскадные синхронные REST-вызовы к страховым компаниям
- `ins-product-aggregator` агрегирует ответы 5 (а скоро 10) внешних API в одном синхронном запросе.
- Любая задержка / таймаут / 5xx у одного партнёра увеличивает время ответа всей цепочки.
- При запросе `core-app → ins-product-aggregator → 10 страховых компаний` риск отказа возрастает мультипликативно (`P(success) = Π pᵢ`).

### 2. Polling вместо событий
- `core-app` опрашивает агрегатор каждые 15 минут — данные устаревают, нагрузка на API партнёров постоянная даже без бизнес-необходимости.
- `ins-comp-settlement` запускает ночной job — при сбое страховые компании получают данные с задержкой ≥ сутки.

### 3. Жёсткая связность core-app ↔ ins-comp-settlement
- `ins-comp-settlement` ежесуточно делает REST-запрос к `core-app` за списком оформленных страховок.
- При увеличении объёма выгрузки запрос становится тяжёлым, нагружает основную транзакционную БД `core-app`.
- Сбой одного из сервисов в момент ночного запуска приводит к расхождению реестров.

### 4. Локальные реплики данных без гарантий доставки
- Реплики продуктов в `core-app` и `ins-comp-settlement` обновляются «по расписанию» — нет гарантии консистентности между сервисами.
- Если в момент обновления у `ins-product-aggregator` была ошибка взаимодействия с одной из страховых, реплика будет содержать неполные данные, и это распространится на оба потребителя.

### 5. Дублирование интеграционной логики
- Логика обращения к 10 страховым компаниям и парсинга их ответов сосредоточена в одном синхронном пути — изменения у одного партнёра вынуждают релизить весь агрегатор.

## Риски при росте нагрузки и числа партнёров

| Риск | Сценарий | Бизнес-эффект |
|------|----------|---------------|
| Увеличение latency | Каждый новый партнёр добавляет задержку в синхронный pipeline | Нарушение SLA, ухудшение NPS |
| Каскадные сбои | Падение одного API партнёра → таймаут агрегатора → таймаут `core-app` | Падение сайта, ~500 тыс. ₽/час потерь |
| Перегрузка БД core-app | Ночной запрос ins-comp-settlement при росте объёма страховок | Деградация дневной нагрузки на следующий день |
| Расхождение данных в реплицируемых каталогах продуктов | Сбой в момент 15-минутного poll | Продажи неактуальных тарифов, претензии партнёров |
| Невозможность горизонтального масштабирования агрегатора | Чем больше потребителей — тем выше RPS к страховым | Партнёры применяют свой rate-limit, отдают 429 |
| Отсутствие отказоустойчивого ретрая | Потерянный ответ страховой = потерянное обновление | Невыплаты комиссий, финансовые риски |

## Предлагаемые архитектурные решения

### 1. Event-Streaming через Kafka (или Yandex Data Streams / YDB Topics)
- Топик `product-catalog.updated` — `ins-product-aggregator` публикует обновления продуктов и тарифов; `core-app` и `ins-comp-settlement` подписываются.
- Топик `policy.issued` — `core-app` публикует факт оформления страховки; `ins-comp-settlement` подписывается и накапливает реестр в реальном времени.
- Снимает ночные REST-выгрузки и синхронные poll-цепочки, развязывает сервисы по времени и доступности.

### 2. Transactional Outbox в `core-app` и `ins-product-aggregator`
- Изменения в БД и публикация события — в одной локальной транзакции через таблицу `outbox`.
- Отдельный relay читает `outbox` и публикует события в Kafka.
- Гарантирует at-least-once доставку даже при сбоях брокера.
- В консьюмерах (`core-app`, `ins-comp-settlement`) — идемпотентная обработка по `event_id`.

### 3. Декомпозиция взаимодействия с партнёрами
- `ins-product-aggregator` опрашивает страховые **асинхронно** в фоне и кэширует ответы.
- Synchronous-REST оставляем только для on-demand сценариев (например, запрос конкретного ОСАГО-предложения — это закроет Task 4).
- На вызовы партнёров навешиваем Circuit Breaker + Retry + Timeout.

### 4. Сохранение REST для UI и B2B-API
- Внешний контракт не меняем — внутри пайплайн становится событийным.

## Итог
Переход на Event-Driven архитектуру с Outbox устраняет три ключевые проблемы (синхронные каскады, polling, ночные REST-выгрузки) и подготавливает систему к удвоению числа партнёров без линейного роста latency и точек отказа.
